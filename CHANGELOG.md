## [1.5.0-rc02] - 2026-07-01 [PUBLISHED]

### Fixed
- **`Dialog` — two open dialogs no longer ping-pong focus into a `RangeError` (browser freeze)** - `Dialog` wraps `<fluent-dialog>`, whose FAST implementation defaults `trapFocus` to true and installs a document-level `focusin` listener that yanks focus back inside whenever it escapes (this isn't even gated on `modal`). With two dialogs open at once — e.g. opening a user-picker dialog from inside an already-open dialog — both traps fire on every focus change: A pulls focus to A → B's listener sees focus left B and pulls it to B → A's listener pulls it back → synchronous infinite recursion that overflows the call stack (FAST's `focusFirstElement` ↔ `handleDocumentFocus` has no reentrancy guard, and its `shouldForceFocus` only checks whether *this* dialog contains the focused element, so neither instance yields). Fixed at the wrapper level using the existing global `openDialogStack`: a `syncFocusTrap()` keeps the trap active on only the topmost open dialog and releases it on every dialog beneath; closing the top re-traps the new top. The catch — and the reason an earlier pass at this still froze — is that setting FAST's public `trapFocus` *property* to `false` does **not** tear down the `focusin` listener: the value flips but `isTrappingFocus` stays `true` and the listener keeps firing (FAST's `trapFocusChanged` reflection doesn't drive the teardown reliably; verified live — `el.trapFocus = false` leaves `isTrappingFocus === true`, only `el.updateTrapFocus(false)` clears it). So `syncFocusTrap()` calls FAST's internal `updateTrapFocus(shouldTrap)` directly to force the listener on/off immediately, and sets the property only to keep FAST's own `shouldTrapFocus()` coherent. It only ever *forces the trap off* — a dialog the author opened with `trapFocus={false}` is never silently re-enabled. (`updateTrapFocus` is an undocumented internal method, optional-chained so a future `@fluentui/web-components` that renames it degrades to a no-op rather than throwing; worth re-checking on the next FluentUI bump.) No fork of `@fluentui/web-components` required.
- **`Dialog` — modal dialogs now lock page scroll, so wheeling over the dialog no longer scrolls the page behind it** - The modal overlay is a translucent `<div>` that doesn't capture wheel events, so when the pointer sat over a non-scrollable region of the dialog (the header, a `<Tabs>` strip, gaps between fields) the wheel scroll chained up to the nearest scrollable ancestor — the document — and scrolled the page behind the modal. `overscroll-behavior` can't fix this because there's no scroll container directly under the pointer to contain the scroll. Added a reference-counted body scroll lock in `Dialog.svelte`: a new `$effect` engages `document.body { overflow: hidden }` while `visible && modal` and releases it on close/destroy via the effect cleanup. The lock is counted so stacked/nested modals only release once the last one closes, saves and restores the original inline `overflow` / `paddingRight`, and compensates for the disappearing scrollbar width (adds matching `padding-right` to `<body>`) so the page doesn't shift sideways when the lock engages. Gated on `modal` — non-modal dialogs intentionally leave the page scrollable.

### Changed
- **`Option` no longer wraps `<fluent-option>` — renders a plain themed `<div role="option">`, making `Select`/`Combobox` dropdowns open ~15× faster** - Now that `Select`, `Combobox`, and `Autocomplete` are all custom components that own their listbox, style rows with design tokens, and drive highlight/filter/selection via data-attributes, the underlying `<fluent-option>` (a FAST custom element with its own shadow DOM) was pure cost: opening a dropdown had to construct and upgrade one custom element per option, which blocked the main thread — measured at **~185ms to open a ~60-option `Combobox`** (a visible lag on click; the mode — inline/list/both — made no difference, and single-select `Select` had the same cost via the same portalled-copy + hidden-mirror pattern). `Option.svelte` now renders a plain `<div role="option">` styled entirely with FluentUI design tokens (matching the approach `Autocomplete`'s option rows already used), so options render instantly: the same `Combobox` now opens in **~12ms**. The public `<Option value=… label=… data=… icon=… selected=… disabled=…>` API and the `selected-options` context contract are unchanged, so this is a drop-in with no consumer changes. Internally: the option's value moved from a custom-element `value` property to a `data-value` attribute (removing the property-vs-attribute quirk the parents special-cased); selection is reflected via `aria-selected`; and row layout/hover/keyboard-highlight/selected/disabled/filtered-out styling now lives once in `Option.svelte` (scoped to the option element, so it applies in both the portalled popover and the inline multi-select list) instead of being duplicated in each parent. The `fluentOption()` FAST registration was dropped from `Option`, `Select`, and `Combobox`.
- **`OptionItem.disabled` is now optional** - The `disabled` field on `OptionItem` (used by `Combobox`/`Select` option arrays) was required, forcing every option literal to spell out `disabled: false`. It's now `disabled?: boolean` — omitting it means "not disabled", matching how `Option` already defaults it. Non-breaking (existing code that sets `disabled` still compiles). `OptionItem` and `SelectedValue` are now also re-exported from the package root.
- **`Combobox` — rewritten as a custom component; dropdown no longer grows unbounded or gets clipped by an `overflow` ancestor (e.g. a `Card`)** - The old `Combobox` wrapped `<fluent-combobox>`, whose listbox renders *in place* (`position: absolute` inside the component) and sizes its `max-height` against the **window** viewport, not its actual container. Two symptoms followed from that single design fact: (A) on a tall page the listbox sized itself to fit dozens of options because "space down to the window bottom" was huge, so it looked unbounded; and (B) since it lived inside the form's `Card`, anything past the card's `overflow: hidden/auto` edge was clipped — the bottom of the dropdown disappeared under the card. No CSS cap can fix B because the listbox can't escape an ancestor's clipping context. `Combobox` is now a custom component built on the same `PositioningRegion` portal that `Select` uses: the dropdown is portalled out of the card and its height is capped to the real available viewport space (Floating UI `size` middleware → `--available-height`), so it stays on-screen and scrolls instead of overflowing. The trigger is an editable `<input>` that filters options as you type (diacritic-insensitive), with the `autocomplete` modes preserved — `list`/`both`/default filter the dropdown, `inline`/`both` auto-complete the typed text, `none` neither. Options come from either the `options` array or `<Option>` children (both filter identically via a per-option `data-filtered-out` toggle), and `<Option>` selection still flows through the shared `selected-options` context. The public API is unchanged — `value: string[]` (bindable), `options`/children, `onchange`, `minSearchLength`, `position`, `appearance`, `disabled`/`required`/`open`/`name`/`label`/`labelTemplate`/`ariaLabel`/`width` all behave as before — so this is a drop-in replacement. `currentValue`, `height`, and `multiple` are still accepted but are no-ops (a combobox is single-select; for multi-select with chips use `Autocomplete`). `minSearchLength` now gates **every** open affordance, not just typing — clicking the input, clicking the chevron, and ArrowUp/Down all keep the dropdown closed until at least `minSearchLength` characters are typed, and deleting back below the threshold re-closes it (previously the threshold was only enforced on the typing path, so a click opened the full list immediately — defeating the point of the gate on large/async option sets). Keyboard support: ↑/↓ to move, Home/End, Enter to commit the highlighted option, Esc to close, Tab to close without committing. This removes the last `<fluent-combobox>` wart and makes `Combobox` consistent with the custom `Select` (same positioning, theming, and a11y).

### Added
- **`Combobox`/`Select` — grouped options via a new `OptionGroup` component and an `OptionItem.group` field** - Options can now be sectioned under non-interactive, labelled headers. Two ways: (1) add a `group` string to each item in a `Combobox` `options` array — the combobox sections them in **source order**, starting a new header wherever the `group` value changes, so ungrouped items stay exactly where you place them (leading, trailing, or between groups) and a group that reappears simply emits its header again; (2) wrap `<Option>` children in `<OptionGroup label="…">` (works in both `Combobox` and `Select`, the only grouping path for `Select` since it has no `options` array). Each group renders `role="group"` with an `aria-label` and a themed header — a sticky, filled, uppercase label band with a top divider that stays pinned while you scroll its options, and the group's rows are indented so they read as nested under it (distinct from flush ungrouped rows). Keyboard navigation (↑/↓, PageUp/Down, Home/End) and filtering only ever walk the option rows, so headers are skipped, never highlighted, and not counted. In `Combobox`, an entire group (its header included) disappears automatically once all of its options filter out — done with a live CSS `:has()` rule, so no orphan headers linger as you type. New export: `OptionGroup`; `OptionItem` gains an optional `group` field.
- **`Combobox` and `Select` — PageUp/PageDown keyboard navigation** - Both dropdowns now move the highlighted option by a full page on PageDown/PageUp (in addition to the existing ↑/↓, Home/End). The page step is computed from how many option rows fit in the listbox viewport (rows-per-viewport minus one for context), so it adapts to the dropdown's height; pressing them while closed opens the dropdown. Makes long option lists navigable without holding the arrow keys.
- **`Combobox` — search callbacks: `onsearch` (server-side, parent-owned) and `filter` (custom client-side matcher)** - The `Combobox` was purely client-side — it rendered the whole option set and filtered it in place. Two new, composable hooks let it drive real search: (1) **`onsearch: (query) => void`** — a debounced (see `searchDelay`, default 250ms) notification that the query changed. When provided, the parent owns the data: you fetch results and update the `options` prop, and the component **skips its own filtering** (the server already filtered) and re-syncs the list when the new options land. Pairs with `minSearchLength` (don't fire on the first character) and a parent-controlled `loading` flag that shows `loadingText` ("Searching…") instead of the empty-state while a request is in flight. An internal pending flag also covers the debounce gap, so the "No results found" message never flashes between a keystroke and the results arriving — even if you don't wire `loading`. (2) **`filter: (query, option) => boolean`** — replaces the built-in diacritic-insensitive substring match with your own predicate (fuzzy, token, match-on-`data`, …) while staying fully client-side; ignored when `onsearch` is set. The `filter` callback receives a `ComboboxFilterOption` (the `OptionItem` plus its optional `data` payload). Async mode also caches the selected option's label at selection time, so the input keeps showing the right text after the chosen option scrolls out of the (churning) result set. New props: `onsearch`, `searchDelay`, `filter`, `loading`, `loadingText`. New exported types: `ComboboxFilter`, `ComboboxFilterOption`.
- **`Combobox` — empty-state message when the filter matches no options** - Typing a query that matches nothing previously left just an empty, tiny dropdown box with no explanation. The dropdown now renders a centered "No results found" message when zero options remain after filtering. Customizable via the new `noDataText` prop (string, default `"No results found"`) or, for full control, the `noDataTemplate` snippet which overrides it. The message is driven by a live count of displayed rows (disabled options still count as displayed) and is reset on close so it never flashes on the next open.
- **`Dialog` demo — new "Tabs inside a height-constrained Dialog" example demonstrating scroll containment** - A fixed-height `<Dialog>` whose body is a `<Tabs>` set to fill the available height, with a tall expression form (mirroring a real-world report where the textarea grew out of the dialog) inside the Expression panel. A live checkbox toggles the containment pattern: with it off, the tab panel is a plain block that neither fills nor scrolls, so content taller than the dialog overflows and spills past the dialog bounds; with it on, `.fluent-tabs-panels` becomes a flex column and the active `.fluent-tab-panel` gets `flex: 1; min-height: 0; overflow-y: auto`, so the panel fills the remaining dialog height and scrolls its own overflow. Documents the consumer-side pattern for putting `<Tabs>` inside a height-constrained `<Dialog>`.

## [1.4.1] - 2026-06-25 [PUBLISHED]

### Fixed
- **`MultiSplitter` — splitters mounted inside hidden tab panels (or any `display: none` parent) now render with proper pane widths on first reveal instead of being stuck at 0 px** - When a `MultiSplitter` mounted inside an inactive `<Tab>` panel — or any element with `display: none` at construction time — `rootEl[clientAxis]` returned 0 during `applyInitialSizes`, so every pane was assigned `flex-basis: 0px`. The installed `ResizeObserver` then short-circuited via `if (lastTotal <= 0) { lastTotal = total; return }` when the panel first became visible, locking panes at zero width with no path back to their declared `min` / `size`. Three coordinated changes in `MultiSplitter.svelte`: (1) `scheduleInit` now installs the `ResizeObserver` and the `[data-multisplitter-toggle]` click delegation immediately even when the container is still hidden, so the observer is ready to catch the 0 → non-zero transition; (2) `applyInitialSizes` bails early when `initialTotal <= 0` without marking `initApplied`, deferring the work until the container is actually laid out, plus a new idempotency guard so repeated calls from the observer don't re-init; (3) the `ResizeObserver` callback gains two new branches — `total <= 0` records `lastTotal` and returns without touching pane sizes (was destructive: `clampToConstraints(0, ...)` zeroed every basis on tab-hide, losing the user's layout on the next reveal), and `!initApplied` runs the deferred `applyInitialSizes` on the first reveal. The existing `if (lastTotal <= 0) { lastTotal = total; return }` short-circuit is gone — the path now falls through to the scale logic so a reveal-after-resize-while-hidden rescales pane sizes proportionally instead of overflowing the new container width. Net result: splitters inside tabs, accordions, modals-not-yet-open, or any other initially-hidden parent honour their constraints on first reveal, and hide/show cycles preserve the user's drag-state. Demo added at `/components/navigation-layout/multisplitter` under "Inside tabs (deferred initial sizing)".

- **`CommandPalette` — keyboard-shortcut chips in the footer (`↑`, `↓`, `↵`, `Ctrl`, `K`) are now legible instead of fading into their own background** - The `.cp-footer` rule set `color: var(--neutral-foreground-hint)` so the "navigate" / "open" / "toggle" labels render as gray-on-white against the panel surface (decent contrast). But `.cp-footer kbd` has its own opaque `background: var(--neutral-layer-2, #f5f5f5)` for the boxed-key look, so the hint color cascaded into the kbd boxes — text at #888 on background at #f5f5f5 at 0.7 rem font-size — and the actual arrow / Ctrl / K glyphs basically vanished against their backdrop. Added explicit `color: var(--neutral-foreground-rest, #222)` on `.cp-footer kbd` so the kbd contents resolve against full foreground-on-layer-2 contrast while the surrounding labels keep their hint color.

- **`TopNav` — `drawerPinned={true}` (the desktop rail) no longer closes on every link click** - `TopNav`'s internal `closeMobileMenu` was unconditionally setting `mobileMenuOpen = false`. The recommended docs-layout pattern wires `onClick={closeDrawer}` on every `NavLinkItem` so the mobile overlay dismisses on link tap — but on desktop, with `drawerPinned={true}`, that same wiring closed the pinned rail too. The `$effect` that syncs `mobileMenuOpen` to `drawerPinned` only re-runs when `drawerPinned` itself changes, so once the rail collapsed it stayed collapsed until the consumer toggled the prop or resized the viewport. `closeMobileMenu` now early-returns when `drawerPinned` is true, matching the documented contract that a pinned drawer is meant to stay open across link clicks. Mobile (overlay) behavior is unchanged — `closeDrawer` is still the correct way to dismiss the drawer on tap.

### Internal
- **Dependency security updates — 8 of 9 npm audit advisories resolved (3 high, 5 moderate, partial low)** - Targeted bumps via `npm update <pkg>` rather than `npm audit fix` so each change could be tested in isolation. Resolved: `ws` 8.20.0 → 8.21.0 (uninitialized memory disclosure + DoS), `devalue` 5.7.1 → 5.8.1 (sparse-array DoS), `vite` 7.3.2 → 7.3.5 (NTLMv2 hash disclosure + `server.fs.deny` bypass on Windows), `brace-expansion` (transitive numeric-range DoS), `qs` (comma-format stringify DoS), `postcss` 8.5.x → 8.5.15 (XSS via unescaped `</style>`), `svelte` 5.55.3 → 5.56.4 (4 SSR/XSS/ReDoS advisories), `@sveltejs/kit` 2.57.1 → 2.67.0 (`query.batch` cross-talk), `cookie` chain cleared via existing `overrides` (nested `cookie@0.6.0` under `@sveltejs/kit` → 0.7.2). Only `esbuild` 0.27.x dev-server file-read low (Windows-only, local-network attacker) remains — `0.28.x` was deferred because it broke dev-mode output emission in this project's pipeline. None of the resolved packages are runtime dependencies of the published `svelte-fluentui` artifact (all devDeps / transitive devDeps), so no consumer-visible behavior change — this is hygiene for the build/dev environment.

- **`docs/svelte.config.js` — restored explicit TypeScript preprocessing via `vitePreprocess({ script: true })`** - Newer `@sveltejs/vite-plugin-svelte` (and `create-vite 9.0.0` from 2026-03-12) made `vitePreprocess()` skip TypeScript by default — Svelte 5's native parser handles most TS, but trips on edge cases like curried arrows with typed optional params + return-type annotation (`docs/src/routes/applications/form-validation/+page.svelte`), and in dev the unprocessed `?`/`??` operators reached the browser as `SyntaxError: Unexpected token '?'`. Passing `{ script: true }` re-enables the explicit script preprocessor. This was the iceberg blocker for the dep upgrades — once the config was fixed, svelte 5.56.x and kit 2.67.x became safe to bump.

- **`package.json` overrides — defensive version pins added** - To prevent future `rm package-lock.json && npm install` or `npm update` from regressing back into broken state, pinned: `vite ^7.3.5`, `esbuild ~0.27.7` (explicitly NOT 0.28.x — known to break dev output), `ws ^8.21.0`, `devalue ^5.8.1`, `@sveltejs/vite-plugin-svelte 6.2.4`. The existing `cookie ^0.7.2` override is unchanged.

## [1.4.0] - 2026-06-22 [PUBLISHED]

### Added
- **`MultiSplitter` / `MultiSplitterPane` — complete rewrite as a Svelte 5 port of pureadmin.io's `pa-splitter`, replacing the previous unused wrapper** - The old `MultiSplitter` was a thin shell that did almost nothing; it's been replaced with a from-scratch implementation in `packages/svelte-fluentui/src/lib/components/layout/MultiSplitter.svelte` (~1100 lines) plus a sibling `MultiSplitterPane.svelte` (~120 lines) and a shared types module at `src/lib/types/multi-splitter.ts`. Feature set: N-pane resizable container (N≥2), horizontal or vertical orientation, drag-to-resize with a REBALANCE drag model where each gutter resizes its primary neighbour and distributes the matching opposite delta across a contiguous block of non-rail panes on the secondary side (CLASSIC absorber when the immediate secondary is non-rail; TUNNEL absorber that skips over rails when it is, so slack can punch through a rail wall and grow the primary). Minimize-to-rail via `<MultiSplitterPane minimize>`: dragging into the snap zone (`max(railSize * 1.5, railSize + (anchor - railSize) * minimizeThreshold)`) snaps to a `railSize`-wide rail; once railed, gutter drag becomes asymmetric — inward drag is inert (the gutter doesn't move), outward drag past 2px releases the rail, fires `onexpand`, and grows the pane following the cursor with the rail floor clamping until `primary.min` is reached. Dblclick on the gutter and click on the rail body work as alternative expand gestures. Full keyboard navigation on the gutter (`Arrow*`, `Home`, `End`, `Enter`/`Space` to toggle minimize on an adjacent minimizable pane) with proper `role="separator"` + `aria-valuenow/min/max` ARIA. Persistence via `id` prop saves sizes, last-non-zero (restore) sizes, and minimized state to `localStorage` under `fluent-multi-splitter:<id>` in a v2 schema. Accordion mode auto-activates when the container shrinks below the sum of all panes' mins + gutters + gaps + padding (a `ResizeObserver` watches the root) and rails all minimizable panes except one; toggling exits accordion when there's room again. The `--reflowing` class is added for ~250ms after programmatic `applySizes` calls outside a drag to suppress gutter-hover flashes when panes shift under a resting cursor. Drag math is rAF-throttled with a 2px TAP_PX jitter threshold; a programmatic-toggle delegation listener fires on any element marked `[data-multisplitter-toggle]` inside a minimizable pane so consumers can wire custom toggle buttons. Container is content-driven by default (no `height: 100%` baked in — `height` prop opts into fill-parent for IDE-style layouts). Cards inside panes auto-adapt to railed state: `.card` first child becomes the rail title, the rest is hidden, and the title rotates via `writing-mode: sideways-rl` in horizontal-orientation panes only — driven by a pane-level `--horizontal` / `--vertical` class so nested splitters with different orientations don't cross-contaminate styles. Three callbacks: `onresize`, `oncollapse`, `onexpand` with `MultiSplitterResizeDetail` / `MultiSplitterToggleDetail` payloads. Demo at `/components/navigation-layout/multisplitter` showcases four examples: simple two-pane, three-pane with minimize + persistence, vertical orientation toggle, and a fixed-area IDE-style with a nested splitter.

### Changed
- **`Select` — multi-element render tree wrapped in `<div class="select-root" style="display: contents">` so consumers see a single encapsulated component** - The previous Select rendered 2-4 sibling root elements (label + hidden source mirror + trigger button + optional hidden input for form participation in single mode, or label + inline listbox in multi mode), which meant a consumer who positioned a `<Select>` in a flex/grid layout had to know about the internal sibling structure to align it. Wrapped the whole render in a single `<div class="select-root">` and styled it `display: contents` so the wrapper is invisible to layout — flex/grid containers still see the inner elements directly as flex items / grid children, but consumers see one logical component root. Zero behaviour change for existing consumers (the layout cascade is identical via `display: contents`), the only difference is that querying `.select-root` from outside the component now reaches the Select.

## [1.3.3] - 2026-06-10 [PUBLISHED]

### Fixed
- **Custom-element attribute bindings stop stringifying `undefined` / `null` / `false` — 22 wrappers reverted to the conditional-spread pattern** - Recurring regression that the maintainer flagged as having been fixed ~5 months prior and reintroduced during the structural rework at commit `15b3635`. Symptoms on the demo page: `<fluent-text-field title="undefined" ...>` for an unset title, `<fluent-text-field readonly="false" ...>` for `readonly={false}` (with the not-allowed cursor still showing because `[readonly]` CSS attribute-presence selectors match regardless of value), and `<TextField disabled={!canGoBack || disabled}>` rendering `disabled="false"` on the back/forward buttons in Paginator. Root cause is Svelte 5's handling of attribute bindings on custom elements (`<fluent-*>`): for native HTML elements it knows the boolean-attribute spec and removes the attribute when the value is `false`/`null`/`undefined`, but for custom elements it sets properties via the element's setter, and FAST's `@attr` decorators stringify whatever they receive — so `element.title = null` becomes `setAttribute("title", "null")`, `element.disabled = false` becomes `setAttribute("disabled", "false")`, and so on. Neither shorthand (`{title}`) nor explicit nullish (`title={title || null}` / `title={title ?? null}`) escapes this — both still emit a string attribute. The only known-working pattern is conditional spread, which physically prevents the attribute from being declared in the template at all: `{...(title ? { title } : {})}`. Applied across `TextField`, `Textarea`, `Switch`, `Slider`, `Checkbox`, `Button`, `Anchor`, `AccordionItem`, `Accordion`, `BreadcrumbItem`, `DataGrid`, `DataGridCell`, `DataGridRow`, `Dialog`, `Listbox`, `MenuButton`, `Option`, `TabPanel`, `Toolbar`, `NumberField`, `Combobox`, `QuickGrid` (context-menu item) and `Paginator` (back/forward buttons). For `value`-type props where empty string is meaningful (an input the user has cleared), the variant `{...(value != null ? { value } : {})}` is used so `value=""` still renders; for numeric props where `0` is a valid setting (`min`, `max`, `step`, `colIndex`, `rowIndex`, etc.) the variant `{...(attr !== undefined ? { attr } : {})}` is used so `0` doesn't get treated as falsy. `Search`, `Radio`, and `RadioGroup` already used this pattern post-rework — they're the proof points that confirmed the approach works. Net behavior consumers will see: `disabled={false}` and `readonly={false}` truly omit the attribute (no more not-allowed cursor on enabled fields), `title={undefined}` renders no `title` attribute (no more browser tooltips showing the literal string "undefined" / "null" on hover), and `value=""` still renders an empty input.

- **`TextField` demo page — added Readonly and Disabled example sections** - The `/components/forms/text-field` showcase previously only demonstrated the basic input and the `autocomplete` variants; the readonly and disabled states (the surface that exposed the bug above when toggled on a previously-enabled field) weren't visible from the docs. Two new sections under Examples: Readonly with outline + filled variants displaying a non-editable value, and Disabled with three variants (outline + placeholder, outline + value, filled + value) to cover the common form-rendering shapes.

## [1.3.2] - 2026-06-09 [PUBLISHED]

### Added
- **`Badge` — new `radius?: string` prop overrides the binary rounded-rect / pill shape with an arbitrary border-radius value** - Badge previously had exactly two shape modes baked in: the default `var(--control-corner-radius, 4px)` rounded rect and `circular={true}` which switches to `var(--fluent-border-radius-pill)`. That binary mirrors Microsoft's FluentUI Badge `shape` prop (rounded vs circular) and the design intent that badges should pick one of the two canonical shapes, but it left no per-instance escape hatch — a consumer who wanted a slightly-rounder badge (e.g. `8px` to match a nearby Card corner) or a softer-rect look had to drop down to inline `style="border-radius: ..."`. The new `radius` prop accepts any CSS length / value and emits `border-radius: ${radius}` as inline style, so it wins over both the default class rule and the `.badge-circular` override via natural CSS specificity (inline > class). When unset (the default), badges render at the existing token-driven radius, so no consumer is affected. Plays nicely with `circular={true}`: setting both is supported and `radius` wins — useful for cases where the consumer wants the circular-mode `min-width: 20px; padding: 2px 6px` sizing but with a non-pill radius. Kept as a string prop (not number) so consumers can pass any CSS unit (`8px`, `0.5rem`, `50%`, `var(--my-radius)`) — the binary `circular` boolean stays as-is for the common "I want a pill" case without needing to remember the exact pill token value.

- **`TopNav` — new `menuToggleSize?: number` (default `42`) + `menuToggleTemplate?: Snippet<[{open: boolean; toggle: () => void}]>` props let consumers tune or fully replace the hamburger toggle without forking** - Previously the toggle was a hardcoded 42×42 fluent-button with a fixed `☰` glyph, so any consumer who wanted a larger touch target, a different icon, or a brand-styled button had no recourse. Two escape hatches at different levels: `menuToggleSize` (the common case) flows through a new `--topnav-toggle-size` CSS custom property set inline on `<nav>`, so the default button's width/height plus the glyph's `font-size` (now `calc(--topnav-toggle-size * 0.55)` instead of a hardcoded `1.5rem`) and the close-icon's pixel size (now `Math.round(menuToggleSize * 0.48)` instead of a hardcoded `20`) all scale proportionally — bumping `menuToggleSize` to 56 grows the icon along with the box instead of leaving a tiny glyph in a big square. `menuToggleTemplate` (the override case) receives `{open, toggle}` so the consumer can render any button shape (text + chevron, brand-styled accent button, custom SVG icon) and still wire up the state correctly. Crucially both default and custom paths render inside a new wrapper `<div class="topnav-menu-toggle">` that owns the visibility/order/collapse rules (`display: none` by default, `display: flex` at `@container topnav (max-width: 960px)`, plus the `collapse="always"` and `drawer-pinned` overrides) — so a custom template automatically inherits the same hide-when-wide / show-when-narrow / stay-visible-when-pinned behavior without consumers needing to know the internal CSS structure. The wrapper deliberately doesn't force size on its children so a custom "Menu" text button renders at its natural width instead of being squashed into a 42×42 square. Size + slot is two clear knobs at the right granularities; we considered exposing a separate `menuIcon`/`menuCloseIcon` glyph slot but rejected it as a third middle layer that adds API surface without covering meaningfully new cases (a consumer who wants a different icon already has `menuToggleTemplate`).

### Changed
- **`TopNav` — default hamburger replaced fluent-button with a plain `<button>` styled as a borderless icon target** - The previous default rendered `<Button appearance="stealth">` (a fluent-button web component), which still carried button chrome — a hover background fill, the boxed visual weight of a stealth button, and required `::part(control)` overrides to defeat its internal padding/min-height so the icon would actually center in the 42×42 box. Read as "button containing an icon" instead of "clickable icon". Replaced with a vanilla `<button type="button">` styled with `background: transparent; border: none; padding: 0; color: inherit`, with `opacity 0.7` on `:hover` for affordance (no background fill — the icon itself dims slightly) and a `:focus-visible` outline (`2px solid var(--accent-fill-rest)`) so keyboard navigation stays accessible without showing a focus ring on mouse clicks. The `::part(control)` override CSS is gone (no fluent-button anymore so no shadow part to target) along with the now-unused `Button` import. Visible behavior: the toggle now reads as just the hamburger glyph (or `DismissIcon` when open), not as a chunky button — what consumers using the default surface get without any opt-in. Side effect: the pre-existing svelte-check error on `aria-expanded` is gone, because plain `<button>` accepts ARIA attributes natively via the DOM, instead of requiring them to be declared on Button.svelte's `Props` type. Click target still fills the full `menuToggleSize` box for touch reachability — only the visual weight changed.

### Fixed

### Changed
- **`Select` — rewritten as a custom component (was: `<fluent-select>` wrapper)** - Implementation gotchas worth remembering for future work in this area: (1) `<fluent-option>` stores `value` as a JS PROPERTY, not an HTML attribute — Svelte's custom-element binding path detects the property on the element prototype and uses `el.value = …` rather than `setAttribute`, so `getAttribute("value")` always returns `null` and any DOM-driven lookup must read the property first (helper `optionValue(el)` does this with attribute fallback). (2) The portalled listbox unmounts when the dropdown closes, so a single-mode trigger that resolves its display text from the live listbox would go blank after every selection — fixed by always mounting a hidden `<div class="select-options-source" aria-hidden="true">` mirror of `<Option>` children outside the popover; `getOptionText()` falls back to it whenever `listEl` is null. (3) Type-ahead `c`-then-pause-then-`c` was getting "stuck" on the same option after the 750ms buffer-reset because single-char buffers were being treated as prefix-search (start from current) — added a `isSingleRepress` check: when the buffer is one char AND the currently-highlighted option already starts with that char, treat it like the repeat-mode cycle (start from current+1), so repeated single-key presses always advance regardless of buffer timing. (4) Multi-mode `maxVisibleOptions` was visually overflowing because flex children default to `flex-shrink: 1` and the listbox was a fixed-height flex column — added `flex-shrink: 0` on options so they keep their natural row height and the container scrolls instead of compressing. Keyboard-cursor highlight is reflected via a `data-highlighted` attribute set in a `$effect` keyed on `highlightedIndex`, styled with `background: var(--neutral-fill-stealth-hover)` so the active row is distinct from hover and selected states.

  **Original rewrite rationale:** `<fluent-select>`'s dropdown listbox is rendered inside its own shadow DOM and positioned `position: absolute` relative to the host, with a static `--max-height` that isn't computed from actual viewport space. Inside a Dialog (or any container above the trigger), the auto-positioning correctly picked `position="below"` (the trigger sat near the top of the viewport, so there *was* more room below), but the listbox's max-height exceeded the remaining viewport space and the bottom of the option list extended past the screen edge with no internal scroll cutoff. The old wrapper also carried duplicated markup branches (a `needsScrollContainer` path and a fallback path rendered nearly-identical `<fluent-select>` markup) and a MutationObserver workaround re-applying `value` after init because fluent-select only reads `current-value` once — both byproducts of fighting the underlying web component rather than owning the behavior. Replaced with a custom Select.svelte: in single mode a button-styled trigger renders the selected option's text, and on open a `<div role="listbox">` is portalled to `document.body` via `PositioningRegion` (the same Floating-UI-backed positioner Autocomplete already uses), so the dropdown escapes any `overflow: hidden` ancestors and never gets clipped by container scrolling. The portalled listbox sets `max-height: var(--available-height, 280px)` and the `availableHeight` middleware (see PositioningRegion entry below) writes the computed remaining viewport height into that custom property on every reposition, so flip + size + shift cooperate to keep the list inside the viewport regardless of where the trigger sits. Keyboard wiring covers ArrowUp/Down (move highlight), Home/End (jump to first/last), Enter/Space (commit highlighted), Escape (close), Tab (close without re-focusing), and single-character type-ahead — including the cycle-through-matches-on-repeat behavior the Select demo at `/components/forms/select` exercises with the language list. Type-ahead on a closed trigger opens the dropdown and jump-highlights (user presses Enter to commit) rather than mutating value silently. Multi mode renders an always-expanded inline `<div role="listbox" aria-multiselectable="true">` matching FluentUI Blazor's FluentSelect (Blazor explicitly notes "the current underlying web component does not support a dropdown" when `multiple` is true), with `maxVisibleOptions` still capping visible row count via measured option height. `<Option>` children are unchanged — they read selection via the `'selected-options'` Svelte context which Select now provides directly (with mode-aware semantics: single = always set, multi = toggle) instead of going through the `createSelectedOptions` store, because the store's single-mode `toggle` would deselect on re-click of the already-selected option which is wrong UX for a dropdown. Hidden `<input type="hidden">` renders alongside the trigger when `name` is set, so the component still participates in native HTML form submission despite the trigger being a `<button>` rather than a real `<select>`. Outside-click handled via a capture-phase `pointerdown` listener gated on `isOpen` that walks `composedPath()` and ignores events whose path includes the trigger or the listbox. Public API mostly unchanged: `id, class, style, open (bindable), position ("above"|"below" forces flip side; default auto), multiple, disabled, appearance ("outline"|"filled"), required, autofocus, name, value (bindable), label, labelTemplate, ariaLabel, title, width, height, maxVisibleOptions, indicatorTemplate, children, onchange`. `value` type widened to `string | string[]` to support multi mode without a separate component. Behavioral changes worth noting: `position` now means "forced placement" rather than the previous fluent-select static attribute — when omitted, the dropdown auto-flips via Floating UI; the previous `open` prop was passthrough-only and now binds two-way; the duplicated `needsScrollContainer` wrapper element is gone, so layout-sensitive callers won't get an extra `<div>` in the DOM around the control.

- **`PositioningRegion` — new `availableHeight` prop exposes remaining viewport height as the `--available-height` CSS custom property on the floating element** - The component already wraps Floating UI with `flip()` + `shift({padding: 8})` + `size()` for `matchWidth`, but the `size` middleware's `availableHeight` value (the room left for the floating element after placement + shift) was unused. Consumers building dropdowns had no way to cap the floating content's max-height to actual remaining viewport space — they could either hard-code a `max-height: 300px` (overflows on small screens / when the trigger is near an edge) or skip the cap entirely (overflows always). New `availableHeight?: boolean` prop, when true, adds the size middleware with `padding: 8` (matching the shift padding so the cap accounts for the same gutter) and writes `--available-height: {Nx}px` onto the floating element on every reposition via `elements.floating.style.setProperty(...)`. Consumers set `max-height: var(--available-height, <fallback>)` on a scroll container inside the floating element; the fallback covers the case where the property isn't set (e.g. browsers without size-middleware support, or initial paint before the first compute). Works alongside `matchWidth` — when both are true, a single `size()` middleware instance applies both adjustments in one pass. The new Select rewrite is the first consumer; Autocomplete still uses the old hard-coded `max-height: 300px` since its dropdown is small enough that viewport overflow hasn't been a real issue, but it could opt in trivially in a follow-up.

In `selectMode="multiple"` the returned array is UNIONED with existing `selectedDates` (the clicked day acts as the toggle pivot — if it's already selected, the entire group is removed; otherwise added), so e.g. a "Select3Days" function can be clicked repeatedly to accumulate non-contiguous triplets. In `selectMode="range"` the returned array replaces the range and is reflected back as start=min/end=max so the start/end caps still render. Critically, Calendar no longer re-filters the returned arrays against `disabledDateFunc` — the consumer's functions are authoritative, so they're free to skip disabled days, jump past them to reach a target count, or include them deliberately for special highlight treatments. The hover preview now uses `highlightDates(hoveredDay)` verbatim; in range mode without `highlightDates`, the pre-existing in-progress preview (from `_rangeSelector.start` to the hovered cell) still fires as a fallback so plain Range mode keeps its familiar two-click UX. Two new demos at `/components/forms/calendar`: "Range with SelectOneWeek" (hovering any day highlights Mon→Sun of that week, click commits the whole week) and "Multiple with Select3Days" (hover/click selects the day ± 1 neighbor as a group).
- **`Calendar` — `maxSelectableDays` + `onSelectionError` callback with structured error payload** - Multiple-mode previously had no upper bound, so use cases like "pick up to 5 holiday days" required the consumer to watch `selectedDates`, detect the overflow, undo the addition, and surface a message themselves — racy and verbose. New `maxSelectableDays: number` (multiple/range mode) gates every selection attempt: when a click would produce more than `max` dates (either through union with the existing array in multiple mode, or because `selectDates(clicked)` itself returned a group larger than the cap), the calendar (a) does NOT modify `selectedDates`, (b) fires `onSelectionError` with a structured payload, and (c) clears the hover preview. ### Changed

New exported `FileUploadResult = Partial<Pick<InputFileItem, "metadata" | "downloadUrl" | "thumbnailUrl" | "name">>` widens the handler return to `Promise<void | FileUploadResult>`; whatever the handler returns is spread into the same `patchItem` that flips status to `"completed"`, so the server payload (guid, URL, etc.) lands atomically with the completion flag. Restricted to four fields on purpose — handlers can't accidentally clobber lifecycle fields (`id`, `file`, `size`, `status`, `progress`, `error`). Chunked uploads keep the last non-empty return so the protocol can assign the id up-front in the first chunk or at completion in the final one. Old handlers returning nothing still type-check (the union retains `void`).
- **`InputFile` — `onItemRemove?(item: InputFileItem) => void` callback for server-side cleanup** - Real-world flow: user selects a file → auto-upload returns a server guid → user changes mind and removes the file from the list before submitting the form → server now holds an orphaned upload. New callback fires once per item from `removeAt`, `removeById` (via removeAt), the row `×` button (via removeAt), and per-item from `clear()` / `reset()`. Receives the removed `InputFileItem` with its final status and metadata still intact (captured before mutation; the callback fires after the items array is updated). Consumers check `item.status === "completed" && item.metadata?.serverGuid` and fire `DELETE /api/files/:guid` to clean up. ### Fixed
- **`InputFile` popover's `max-height` was being silently overridden by Floating UI's `size` middleware writing inline `style.maxHeight = availableHeight`** - The `size` middleware ran on every reposition and unconditionally set `floating.style.maxHeight = ${availableHeight - 16}px` regardless of what the CSS rule said. Inline style beats CSS, so the `--fluent-inputfile-popover-max-height` variable (and its previous hardcoded 24rem ceiling) was effectively ignored on any window taller than the cap — the popover ballooned to ~viewport height and the sticky footer ended up pinned far below the visible scroll region, looking like it was floating in the middle of the list. Fix clears the inline override at the start of each `apply`, then reads the CSS-rule-driven `max-height` via `getComputedStyle(floating).maxHeight`, and only re-applies an inline cap when the viewport is actually smaller than that ceiling. So the CSS variable wins on tall screens, the viewport wins on short screens, and consumers can theme the cap without having to also patch the middleware.
- **`InputFile` popover dismissed itself when the user clicked inner buttons (Reset, Pause, +Add more, etc.)** - The click-outside-to-dismiss handler used `popoverEl.contains(e.target)` to decide whether the click was inside the popover. But many inner buttons mutate `items` (or trigger re-renders) synchronously on click, which detaches the original `e.target` from the DOM before the handler reads it, so `.contains()` returned `false` for an element that *was* inside the popover at click time. Two-symptom fix: (1) the dismiss handler now reads `e.composedPath()` at dispatch time — the array is captured before any state mutation can detach the target — and checks containment against three known-good elements (root, selector wrapper, popover); (2) inner buttons that programmatically open the file picker via the hidden `<input type="file">` (the "+Add more" button) call `e.stopPropagation()` so the synthetic click from `fileInput.click()` doesn't bubble back through the root and trip the dismiss path.
- **`InputFile` filename ellipsis never engaged — long names overflowed their row** - `.file-name` had `overflow: hidden; text-overflow: ellipsis; white-space: nowrap` but no flex sizing rule, so in the row's flex layout it took its natural intrinsic width (the full filename), pushing the file size / status / actions off-screen instead of clamping. Added `flex: 1 1 auto; min-width: 0` so the name occupies the leftover row space and can shrink below its intrinsic width — `min-width: 0` is the magic incantation that overrides flex's default `min-width: auto` behavior, which is what was preventing the shrink in the first place.
- **`InputFile` drag-expand overlay didn't dismiss when the user pressed Esc mid-drag** - OS-originated file drags don't reliably fire `dragend` on cancel (the source is outside the browser, so there's nothing to dispatch the event on), so pressing Esc to abandon a drag left `isExternalDragActive=true` and the overlay stuck open until the next drag-and-drop cycle cleaned it up. Added a document-level `keydown` listener that resets the flag on Escape, plus a document `dragleave` listener that fires `relatedTarget === null` when the cursor leaves the viewport (covering the case where the user drags out of the window without dropping). Both join the existing `dragend` / `drop` / `window.blur` dismissal paths.
- **`InputFile` drag-expand overlay flickered when the cursor crossed the underlying card's edge** - The overlay's `ondragleave` handler used `e.target === e.currentTarget` as the criterion for "actually leaving the overlay", but `dragleave` behaves like `mouseout` (not `mouseenter`) — it fires when the cursor moves from a parent element into a child. So when the cursor moved from the overlay's padding area into its inner `drop-zone-content` div, `e.target === e.currentTarget` was true (target was the overlay element), the handler dismissed `isExternalDragActive`, the overlay disappeared, the document's `dragenter` immediately re-activated it on the next pixel of movement, and the overlay reappeared — visible as a one-frame flicker every time the cursor crossed what had been the original card's boundary. Fix uses `relatedTarget` containment instead: the overlay only clears its local `isDragging` highlight when the cursor truly leaves the overlay subtree (`!overlay.contains(relatedTarget)`), and no longer touches `isExternalDragActive` at all — that lifecycle is owned by the document-level handlers exclusively.

- **`Calendar` day-name headers were always Sunday-first regardless of culture** - `getDayNames()` hardcoded `firstDayIndex = 0` with a `"Can't reliably extract this, so default to Sunday"` comment, so a Czech locale calendar showed labels `ne po út st čt pá so` (Sunday-first) sitting above a grid that was actually Monday-first (built via `weekInfo.firstDay` in `getDaysOfWeek` + `startOfWeek`). ## [1.0.0-rc17] - 2026-05-05 [PUBLISHED]

### Added
- **`Field` component — label + hint + validation message + state border for any form control** - FluentUI 2 / Blazor convention factored into a wrapper that owns the label, optional helper text, validation message, and validation-accent border for the slotted form control. `validationState: "none" | "warning" | "error" | "success"` drives both the message color and the bottom-border color of the inner control via `data-state` attribute + CSS shadow parts (`fluent-text-field::part(root)`, `fluent-number-field::part(root)`, etc.). `validationMessage` only renders when state ≠ `"none"` and the message is non-empty (idle fields don't show empty `<small>` elements). `hint` renders neutral helper text below the control when no validation message is showing — the two are mutually exclusive so the message slot doesn't double up. `required` renders a red asterisk after the label (visual only — the inner control still owns native `required`). `orientation: "vertical" | "horizontal"` flips the label position. Mirroring FluentUI 2's bottom-border-only convention, the state border paints only the bottom edge with an inset box-shadow for visual thickness — matches the focus accent treatment so error/success/warning don't look like a different visual idiom from focus. New `_field.scss` partial in `assets/styles/components/`. Works without modifying any existing form wrapper.
- **`ValidationSummary` component — top-of-form error list with jump-to-field links** - Pairs with `Field` for submit-time validation flows. Takes `errors: Record<string, string>` (field-name → message; falsy values filtered out so the panel auto-hides when empty), `labels: Record<string, string>` (field-name → human-readable label, falls back to field name), `title` (default `"Please fix the following:"`), and `onjumpto: (field) => void` callback fired when a user clicks an error link — typical use scrolls to and focuses the offending input. Renders an accessible `role="alert"` panel with `aria-live="polite"`. Styled in a new `_validation-summary.scss` partial. Manual API by design — consumer maintains the errors dict, so it composes with whatever validation strategy the form uses (sync `$derived`, submit-time validate, async, server round-trip). A `Form` context-collecting variant could wrap it later without breaking changes.
- **`Field` & `ValidationSummary` demo page** at `/components/forms/field` — all four validation states side-by-side, label/hint/required combinations, wrapping different control types (TextField, NumberField, Textarea, Select, Search, Combobox, Checkbox), live-validation pattern with touched-on-blur gating, horizontal orientation, ValidationSummary with submit + jump-to-field. Plus full API tables for both components.
- **`QuickGrid` Tab-while-editing now works in `dblclick` / `click` / `button` modes (spreadsheet pattern)** - Previously only `editTrigger="navigate"` had a Tab handler wired up to the editor; in the other modes Tab fell through to the browser's default and blurred the input to whatever happened to be next on the page (often outside the grid entirely), so focus visibly disappeared. The wrapper handler (renamed `handleEditorKeyDownInNavigateMode` → `handleEditorKeyDown`) now intercepts Tab in any mode: commits the current cell, then routes through the new `findNextEditableCell` row-walker (so it skips read-only rows in heterogeneous trees, same as navigate mode). Post-commit advance behavior splits by mode — navigate mode focuses the next `<td>` (which has `tabindex=0`); dblclick / click / button modes auto-open the editor on the next editable cell after one `await tick()` so the previous editor unmounts before the next mounts (without the tick the new editor's autofocus races the old editor's blur). Shift-Tab works the same way in reverse. Boundary check (Tab from the last editable cell on the last row) returns `null` so focus stays put.
- **`QuickGrid` `Ctrl`/`Cmd` + `ArrowLeft` / `ArrowRight` tree expand-collapse in navigate mode** - Standard ARIA tree pattern reserves plain ArrowLeft/Right for tree navigation, but those keys already navigate columns in QuickGrid — `Ctrl`-modified arrows give us the tree action without disambiguation pain. `Ctrl`+`→` expands the focused row if it has children and is currently collapsed (no-op on leaves and already-expanded rows, matching the chevron's affordance). `Ctrl`+`←` collapses the focused row if it's an expanded parent; otherwise walks up to the nearest expanded ancestor via the new `findNearestExpandedAncestor(path)` helper, collapses that, and refocuses the same column on the ancestor's row (since the previously focused leaf is about to be hidden). No-op if the row has no expanded ancestor.
- **`QuickGrid` example mode-switcher on the editable-per-row-type demo** - `/components/quickgrid-tree` "Editable per row type — teams vs employees" gained a radio control above the grid that flips `editTrigger` between `navigate`, `dblclick`, `click`, and `button`. Description text below the radios changes to match the active mode's keyboard contract so users can verify the same row-aware Tab + tree-navigation behaviors work everywhere edit mode applies.
- **`QuickGrid` predefined context-menu types for tree expand / collapse** - Four new `PredefinedContextMenuItemType` values let consumers wire common tree commands without writing the `onclick` / visibility logic themselves: `'expand-all'` and `'collapse-all'` operate on the right-clicked row's branch (matching the file-explorer / IDE convention — per-row "Collapse all" means collapse everything *under here*, not the whole dataset); `'expand-tree'` and `'collapse-tree'` operate on the entire dataset (the rarer power-user "reset everything" action). New `ContextMenuConfig<T> = PredefinedContextMenuItemType | ContextMenuItem<T>` shorthand: `contextMenu={["expand-all", "collapse-all", "expand-tree", "collapse-tree"]}` is the simplest form; users wanting a divider or custom icon use the full-object form with `type: '<predefined>'` to keep the built-in handler. Visibility on the per-row variants gates on `rowHasChildren(ctx.row)` so leaf rows don't get useless menu items; the whole-tree variants gate on dataset state (`treeParentPathSet.size > 0` for expand, `resolvedExpandedPaths.size > 0` for collapse) so they hide when there's nothing to do. Internally a new `setExpandedPaths(next)` helper centralizes the bound-vs-internal expansion-state routing that `toggleExpand` already used. `ContextMenuItem.label` is now optional since the predefined `type` field supplies a default — fully custom items still effectively need a label at runtime. Both tree demos on `/components/quickgrid-tree` were wired up.
- **Form Validation demo page (new)** at `/applications/form-validation` - End-to-end walkthrough of the common validation patterns built on the new `Field` and `ValidationSummary` components: required + format with cross-field check (sign-up form with passwords-must-match), numeric range with custom rule (positive-even-number), debounced async availability check (simulated 600ms backend), conditional required (Department + "Other (specify)"), and submit-time summary with jump-to-field links. Includes a small composable validator-helper recipe (`required`, `minLength`, `pattern`, `numberRange`, plus `runValidators(value, ...rules)`) that's copy-pasteable into consumer projects. Each section's pattern is independent so users can grab whichever approach fits their form. Linked from the sidebar under Applications.

### Changed
- **`/applications/form-validation` refactored to use `Field` and `ValidationSummary`** - Replaced the page's inline `<small class="field-error">` blocks (~30 occurrences) with `validationMessage` props on `Field` wrappers, and the hand-rolled summary panel with a single `<ValidationSummary>` component. Net: ~80 lines of demo code removed; the page now reads as a "how to use the components" tutorial rather than "how to manually wire validation styling."
- **`QuickGrid` navigate mode: all cells are focusable, not only editable ones** - Previously `tabindex={isNavigateMode && isCellEditable(column, item) ? 0 : undefined}` — only editable cells were focusable, which meant in heterogeneous trees the user could never focus a parent (team) row or the read-only tree column, so `Ctrl`+arrow tree navigation couldn't actually be triggered on non-editable rows. Now `tabindex={isNavigateMode ? 0 : undefined}` — every cell is focusable and arrow keys move freely between any adjacent cells. Tab / Shift-Tab still walk through *editable* cells only via `findNextEditableCell`, so the productive Tab-through-fields UX is preserved. Excel uses exactly this split (arrow keys = browse, Tab = jump-to-next-editable).
- **`QuickGrid` focus indicator now applies to any focused cell in navigate mode** - The `.editable-cell.focused` outline rule was extended to `tbody td.focused`, so read-only cells get the same accent outline + neutral fill when focused. `cursor: cell` stays scoped to `.editable-cell` (cursor signals editability, focus indicator signals selection — they're now cleanly decoupled). Without this change, focusing a read-only cell would leave no visible focus indicator and the user wouldn't know where their selection landed.
- **`QuickGrid` arrow keys in navigate mode use simple adjacent-cell movement** - Now that all cells are focusable, ArrowUp/Down move to `rowIndex ± 1` and ArrowLeft/Right move to `colIndex ± 1` regardless of editability. Removed the unused `findNextEditableRow` helper that was a workaround for the previous "editable-only focus" model. ArrowLeft/Right inside an open editor still walk the *editable* column list (the user is mid-edit, so stepping between editable cells matches intent better than browsing); ArrowUp/Down inside an open editor commit and move to any cell on the row above/below.
- **`QuickGrid` bindable-expansion-state demo uses `editTrigger="navigate"`** - `/components/quickgrid-tree` "Bindable expansion state" example switched to navigate mode (without `editable` — derived `isNavigateMode` only depends on `editTrigger`, so keyboard navigation works regardless of the editing master switch). Lets users keyboard-traverse the org tree with arrows + `Ctrl`+arrows and watch the bound `expanded` Set update reactively above the grid.

### Fixed
- **`QuickGrid` Tab traversal correctly skips rows with zero editable columns** - The "row-aware Tab traversal" promise in rc16 had a hole: when stepping off the last editable cell of a row, the handler reused the *current* row's editable column list (`editableCols[0].index`) to focus a column on the *next* row. In a homogeneous editable grid that's fine, but in a heterogeneous tree where some rows have zero editable columns (e.g. a team row in a teams + employees tree), the next row's `<td>` at that column index has no `tabindex` and `.focus()` falls through to body — focus visibly disappeared. New `findNextEditableCell(fromRowIndex, fromColEditableIndex, direction)` helper walks rows in the requested direction, recomputing editable columns per row, and skips rows whose `getEditableColumns(row)` returns empty. Powers Tab and Shift-Tab in both `handleNavigationKeyDown` (cell-level navigation) and `handleEditorKeyDown` (Tab while editing).
- **`Toast` styles now actually ship in the bundle** - The `_toast.scss` partial in `assets/styles/components/` existed and was complete (`.fluent-toast-container`, `.fluent-toast`, position variants, animations) but `main.scss` never `@use`d it, so every consumer pulling `svelte-fluentui/styles.scss` got the toast DOM with zero styling — `position: fixed`, the z-index, the variant colors, the slide-in animation, all missing. Net effect: `toast.success('…')` rendered an unstyled box at the top of normal document flow (top-left of the viewport, above the page header) instead of a styled popover at top-right. The `<style>` block in `ToastContainer.svelte` had a comment pointing at `_toast.scss` but no actual import. Added `@use "assets/styles/components/toast";` to `main.scss`. Verified the rebuilt `dist/main.css` now contains 51 toast-related selectors. Affects every page using the toast service — was probably masked by users not triggering toasts often during recent rc16 testing.

## [1.0.0-rc16] - 2026-05-04 [PUBLISHED]

### Added
- **`QuickGrid` per-row-type editability** - Tree grids and any other heterogeneous dataset can now express "only some rows are editable" without the consumer hand-rolling click-handlers around the grid. Two new shapes, both `boolean | ((row: T) => boolean)`:
  - **Column-level `isEditable` callback** — `column.isEditable: (row) => row.kind === "employee"` lets each editable column decide per-row. Useful when *which* columns are editable depends on the row type (e.g. salary editable on employees, headcount visible-but-read-only on team rows, name editable on both).
  - **Grid-level `isRowEditable` prop** — single predicate that gates the entire row. Use when every editable column is editable for the same set of rows; cheaper than repeating the predicate on every column.
  - Three-stage gate: grid-level `editable` master switch → `isRowEditable` row gate → `column.isEditable` cell gate. All three must pass. Static `false` short-circuits without evaluating the next stage.
  - Navigate-mode `Tab` / `Shift-Tab` traversal is row-aware: `getEditableColumns(row)` is now called per row so the cursor skips read-only cells correctly when stepping through a heterogeneous tree. Cost is one predicate evaluation per row navigated, not per cell rendered.
  - Demo at `/components/quickgrid-tree` → "Editable per row type — teams vs employees": Platform / Product team rows are read-only summaries; double-click on Role or Salary on an employee row enters edit mode, same cells on a team row do nothing.
- **`QuickGrid` `column.nowrap` prop** - Body cells in this column never wrap (`white-space: nowrap`). Three useful combinations:
  - **`nowrap` alone** — single-line cells, column expands as needed to fit the longest value. Best for short identifiers (SKU, code, ID) where wrapping is just visual noise.
  - **`nowrap` + `maxWidth: "…"`** — single-line cells with a hard width cap; long values truncate with an ellipsis. Implementation wraps plain-text cell renders in a `<span class="cell-text">` so a flex child can carry the `overflow: hidden; text-overflow: ellipsis; min-width: 0` (text-overflow doesn't propagate from a flex container to a bare text node, so a wrapper element is required for the ellipsis to actually trigger).
  - **`nowrap` + `autoWidth`** — column sizes to `max(header text, longest cell value)` without either wrapping. Pairs with `fillerColumn` so leftover horizontal space lands on the filler.
  - The header style mirrors the body's nowrap when `column.nowrap` is set, so a body-nowrap column doesn't end up with a wrapping header above single-line cells.
  - Demo on `/components/quickgrid` ("Nowrap columns & ellipsis truncation") shows wrapping vs nowrap+ellipsis side-by-side against a `bio` column with deliberately long values, with explicit `<h4>` labels above each grid.
- **`QuickGrid` component-prefixed CSS variables** - New `--fluent-quickgrid-header-bg`, `--fluent-quickgrid-header-hover-bg`, `--fluent-quickgrid-header-sorted-bg`, `--fluent-quickgrid-stripe-bg`, `--fluent-quickgrid-row-hover-bg` tokens decouple QuickGrid's row/header surfaces from the generic FluentUI `--neutral-layer-*` palette. Themes that overrode `--neutral-layer-2` to a brand color (e.g. DHL yellow on the navbar) used to drag QuickGrid header + striped rows along at the same full-strength saturation, which made data tables visually overwhelming. Now consumers can tint the grid surfaces independently — typically at 10–15 % opacity — while leaving the navbar at full strength. Generated from light/dark `$quickgrid-*` SCSS variables in `_variables.scss`, wired through both theme blocks of `theme.scss`. QuickGrid's CSS uses two-layer fallbacks (`var(--fluent-quickgrid-header-bg, var(--neutral-layer-2, #f5f5f5))`) so existing themes that don't define the new tokens still render identically. Pagination buttons and cell-edit buttons intentionally still use `--neutral-layer-*` since those are buttons, not row surfaces.
- **`Autocomplete` `startIcon` and `endIcon` snippet props** - Decorative snippet slots inside the input at the leading and trailing edge. `startIcon` renders before the input (typical use: a magnifying glass to signal "this is a search box"). `endIcon` renders after, but yields to the auto-rendered clear button (when something is selected) and loading spinner (during async search), so a search icon cleanly swaps to a clear button on selection without fighting it. `:has(.input-start)` / `:has(.input-end)` rules pad the input by 32px on either side in non-inline mode so text never sits underneath the icons. New "Start & End Icons" example on `/components/autocomplete`.
- **`Autocomplete` chip-size CSS variables** - Eight new `--fluent-autocomplete-chip-*` tokens (font-size, line-height, padding-y, padding-x, gap, max-width, text-max-width, remove-padding) drive both inline and external chip geometry. Defaults are in rem so chips scale with root font-size. Themes can override globally (`:root { --fluent-autocomplete-chip-font-size: 0.75rem; }`) instead of monkey-patching component selectors.
- **Site settings store now applies to the document** - `settings` store gains a browser-only subscribe listener that pushes every change to `document.documentElement` as CSS custom properties, plus the `dir` and `data-theme` attributes. Theme mode `'system'` resolves via `matchMedia('(prefers-color-scheme: dark)')` and re-applies on OS-level theme changes. Accent color writes `--accent-fill-rest`/`-hover`/`-active`, mirrors to `--fluent-accent-primary`/`-hover`/`-active`, and computes `--foreground-on-accent-rest`/`-hover`/`-active`/`-focus` via a W3C luminance threshold so dark accents get white labels and light accents (PowerBI yellow) get black labels — without that recompute the OK button on the Site Settings dialog disappeared (white-on-yellow). Neutral base color writes `--neutral-layer-1` and `--fluent-bg-primary`. Direction writes the `dir` attribute. Defensive: non-string accent/neutral values (legacy localStorage shapes) coerce to `#0078d4` / `#FAFAFA` instead of throwing.

### Changed
- **BREAKING — `QuickGrid` column property `editable` renamed to `isEditable`** - The boolean form is unchanged (`isEditable: true` works exactly like `editable: true` did); the new function form (`isEditable: (row) => boolean`) is purely additive. Migration: rename `editable: true` → `isEditable: true` on every column literal. Demo pages at `/components/quickgrid-editable` and `/components/quickgrid-contextmenu` and the `ai/quickgrid.txt` reference were swept. The grid-level `editable` prop is unchanged — it remains the master "is editing turned on at all" switch.
- **`Autocomplete` focus border follows FluentUI 2 textfield convention** - The focus state was painting all four sides of the input with the accent color and adding a 1px outer glow (`border-color: accent + box-shadow: 0 0 0 1px accent`), which broke the FluentUI 2 textfield convention. Now only the bottom edge turns accent (`border-bottom-color`) and an inset box-shadow adds 1px more visual thickness on the bottom only — matches the Blazor reference and avoids any layout shift on focus.
- **`Autocomplete` inline chip size unified with external chip** - Inline chips (inside the input, in `tagsPosition: 'inline'`) had `font-size: 12px` while external chips (above/below modes) had `font-size: 14px`. Same data, same widget — picking a value visually shrunk the chip on its way into the input. Both now use `--fluent-autocomplete-chip-font-size` (default `0.875rem`) and share the same height; the only intentional difference is that external chips have a 1px border (they're standalone, the input's border doesn't enclose them) while inline chips don't (they sit inside the input's existing border).
- **`Tabs` active tab text now tracks accent** - `.fluent-tab.active` color changed from `var(--neutral-foreground-rest)` to `var(--accent-fill-rest, var(--neutral-foreground-rest))` so the active tab's label matches its bottom indicator instead of staying neutral gray. Aligns with the FluentUI Blazor pattern (active tab = accent label + accent indicator).
- **`QuickGrid` sort indicator now tracks accent** - The `▲` / `▼` triangle on the actively sorted column is colored with `var(--accent-fill-rest, currentColor)` instead of inheriting the column header's neutral text color. The unsorted-column placeholder `⬍` stays explicitly neutral with 0.3 opacity so the active sort direction visually stands out.
- **`theme` store localStorage key namespaced** - Renamed `"theme"` → `"fluent-theme"` to prevent collisions with host applications using the same generic key (e.g. PureAdmin saves its theme name like `"audi"` to `localStorage.theme`, which our store then read and discarded as invalid). Migration is automatic — invalid values fall back to `"light"` once; users will need to re-toggle dark mode if they relied on the old key.

### Fixed
- **`QuickGrid` body cells now inherit column width constraints** - `width` / `minWidth` / `maxWidth` / `columnMinWidth` were applied only to the `<th>` header; body `<td>`s carried only `text-align`. In HTML auto table-layout the column's natural width is determined by the *widest* cell across header and body — so a wide body cell (especially one with `nowrap: true`) would drag the column past the header's `max-width`. Net effect on the new nowrap demo: ellipsis wouldn't activate because the column wasn't actually clamped. New `getColumnBodyStyle()` mirrors the same width logic the header uses (including `autoWidth`'s `width: 1%; white-space: nowrap` shrink-to-content trick) onto every body `<td>`, so width caps are now enforced consistently. Side benefit unrelated to nowrap: any grid using `columnMinWidth` will see body cells respect that minimum too, where previously they could squeeze below it.
- **`Autocomplete` single-select mode now actually works** - `selectOption` always appended to `selectedOptions` regardless of `effectiveMultiple`. Net effect in single-select mode: first click appeared to work (`selectedOptions = ['cz']`, `hasSingleSelection = true`, input rendered the picked text), but a second click made `selectedOptions = ['cz','de']` — `hasSingleSelection` then required `length === 1` and went false, `displayValue` fell back to the empty `searchText`, and no chips render in single-select (`showTags` requires `effectiveMultiple`), so the input went mysteriously blank with two values silently held in state. Also `maxSelectedOptions` was being checked even in single-select where it makes no sense. Now: single-select replaces (`[option.value]`), multi-select still appends; the `maxSelectedOptions` cap only gates multi-select; and the dropdown auto-closes after a single-select pick regardless of `keepOpen` (a one-pick widget shouldn't stay open).
- **`Autocomplete` dropdown now closes when the page is scrolled outside it** - `PositioningRegion` anchors the popover to the input on initial open but does not re-anchor on scroll, so scrolling the page would leave the options list floating at its old screen position, visually detached from its anchor. There was a click-outside listener but no scroll-outside listener. Added a `scroll` listener (registered with `capture: true` because most page scroll containers don't bubble scroll events to document) that closes the dropdown when scrolling happens outside both the anchor (`containerElement`) and the popover surface (`.options-list, .positioning-region`). Scrolling inside the options list itself (which is its own scrollable region with `max-height: 300px; overflow-y: auto`) keeps the dropdown open.
- **Site Settings dialog handler unwraps Select detail** - `docs/src/lib/components/SiteSettings.svelte` `handleThemeChange` and `handleAccentColorChange` were passing the entire `Select` event detail (`{value, selectedOption, data}`) to the store setters instead of `detail.value`, which serialized the object into localStorage and broke accent resolution on subsequent loads. Now destructures `.value` matching the package's reference dialog.

## [1.0.0-rc15] - 2026-05-01 [PUBLISHED]

### Added
- **`QuickGrid` tree mode** - New `treePathMember` prop turns the grid into a TreeGrid for ltree-style hierarchical data: each row carries a single path string (PostgreSQL ltree `"1.2.3"`, POSIX-style `"/1/2/3"`, or Windows-style `"C:\foo\bar"`), and one column marked `isTree: true` renders the indent + expand/collapse chevron. Separator is auto-detected by scanning items for `/`, `\`, or `.` (scans through items, not just `items[0]`, so a root row like `"1"` doesn't fool the detector). Optional `treeLevelMember` and `treeParentMember` skip the path-parsing work when those values are pre-computed in the database — coalesces caller-provided values over derived ones. `treeDataSorted` (default `false`) trusts caller's order; otherwise the grid sorts internally by path with numeric-aware segment comparison so `"1.2"` sorts before `"1.10"`. `expandedPaths: Set<string>` is `$bindable`; `defaultExpandDepth` initializes the internal set when not bound, interpreted *relative to the dataset's shallowest level* so a partial-tree / subtree view starting at level 3 still expands its own roots when you pass `defaultExpandDepth={1}`. Filter is ancestor-aware — matched rows force their ancestors visible, and while the filter is active the collapse logic is bypassed so matches inside collapsed branches still appear. Visibility check skips parent paths that aren't actual rows in the dataset (virtual roots), so partial trees render correctly without inventing synthetic root rows. In tree mode, column sort is intentionally disabled to preserve hierarchy. Dedicated demo page at `/components/quickgrid-tree` with three examples (derived-only, pre-computed level + parent, bindable expansion).
- **`QuickGrid` `idMember` prop** - Field on each row that uniquely identifies it. Internal state (drafts, in-progress edits, invalid-cell markers) is now keyed by the value of this field, so pagination, filter, sort, and tree expand/collapse no longer cause an in-flight edit to land on the wrong row when the displayed order changes. Coalesce order in `getRowId(item, displayedIndex)`: `idMember` value → `treePathMember` value (tree mode) → displayed-row index as last-resort fallback. When `editable={true}` is enabled and neither `idMember` nor `treePathMember` is provided, the grid emits a one-shot `console.warn` explaining the consequence (state keyed by displayed index, drifts on re-order) and pointing at the fix.
- **`QuickGrid` `treeDoubleClickBehavior` prop** - `'none' | 'toggle'` (default `'none'`). When set to `'toggle'`, double-clicking anywhere on the tree column toggles expand/collapse on rows that have children — convenient for users who'd rather smash the row than aim at the chevron. Double-click on the chevron itself is ignored (it stops `dblclick` propagation, so chevron stays single-click only — no double-firing). Leaves don't toggle (no children to expand). On the tree column the toggle wins over edit triggers, so users with `editTrigger="dblclick"` or `"navigate"` get tree behavior here; edits can still be initiated by single-click in `'click'` mode or via Enter/F2 in navigate mode. Default text-selection behavior (browser extends the selection on the second click of a dblclick) is suppressed via `mousedown` + `e.preventDefault()` only when `e.detail > 1` AND toggle is enabled AND the row has children — single-click selection elsewhere still works. Demo's org grid defaults to `'toggle'` with a checkbox to flip it.
- **`QuickGrid` per-column `filter` callback** - New `Column.filter?: (filterValue: string, row: T) => boolean | null`. When set, it replaces the built-in case-insensitive substring match for that column. Use cases: numeric ranges (`>500`, `<=10`), date ranges, regex, or multi-field search (`"john doe"` matching `firstName + " " + lastName`). The cell still uses the same per-column filter input as the default substring search — the callback just owns the predicate. Returning `null` signals "input is syntactically incomplete" (e.g. user typed `>` without a number yet) — the grid then ignores this filter (all rows pass) AND adds a `.invalid` class to the input so the user gets a red border instead of an empty grid. Validity is probed against the first row only (the assumption is that validity is a property of the input string, not the data). Demo's Headcount and Budget columns parse `>` / `<` / `>=` / `<=` / `=` operators, return `null` when the input starts with an operator but the number is missing, and fall back to substring match for plain text. Filters against the *raw* row value, not the formatted display string, so a budget formatter `v => "$" + v.toLocaleString()` still searches against the underlying number.
- **`QuickGrid` grid-level `onfilterchange` callback** - `(filters: Record<string, string>) => void`. When provided, internal client-side filtering is bypassed entirely — the grid still renders the filter inputs, fires this callback on every keystroke with a copy of the current `{field: value}` map, and trusts the caller to update `items`. Typical pattern: debounce in the handler, post the filter map to a backend, replace `items` with the result. Pairs cleanly with server-side pagination/sort if you wire those the same way.
- **`QuickGrid` `columnMinWidth` prop** - Grid-level default `min-width` applied to every column header that doesn't specify its own `minWidth`. Useful in concert with `fillerColumn` to stop content-sized columns from collapsing too far when the filler claims leftover space. Skipped on columns that opted into `autoWidth` (whose `width: 1%; white-space: nowrap` shrink-to-content trick would be defeated by a min-width).

### Changed
- **BREAKING — `QuickGrid` `invalidCells` shape: `rowIndex` → `rowKey`** - The bindable `invalidCells: CellValidationState[]` prop now uses `{ rowKey: string, field: string, error: string }` instead of `{ rowIndex: number, field: string, error: string }`. The `rowKey` is whatever `getRowId(item, displayedIndex)` returns (the new `idMember` value, the tree path, or the displayed index as string fallback). Reason: invalid-cell markers shared the same drift problem drafts had — collapsing a parent or paginating could leave a marker on the wrong row. Migration: callers binding `invalidCells` need to read `c.rowKey` instead of `c.rowIndex`. The `onvalidationerror` callback's `detail.rowIndex` is unchanged (still the displayed index, since the callback also passes `row` and the caller can derive the id themselves).

### Fixed
- **`QuickGrid` `fillerColumn` actually absorbs leftover space** - The `.filler-column` CSS was `width: auto`, which doesn't claim any specific share in HTML auto table-layout. Whichever column happened to have the loosest content constraints (typically a column with no `width` set) absorbed the leftover instead, ballooning to fill the row while sibling columns stayed compact. ### Changed
- **Tabs / Tab — full custom Svelte rewrite** - Dropped the `<fluent-tabs>` / `<fluent-tab>` / `<fluent-tab-panel>` web-component wrappers in favor of a first-class Svelte implementation. The previous rewrite attempts (rc09 scroll clip, rc10 scrollbar styling, rc11 host-width cascade, wrap mode) were all losing cascade races against upstream shadow-DOM styles (`:host { display: grid; grid-template-columns: auto 1fr auto }` and `.tablist { width: max-content }`) — author `::part()` rules lost, JS-applied inline styles on shadow parts worked but felt fragile. Replaced with a pure Svelte + design-tokens implementation:
  - **Public API unchanged** — `<Tabs activeId ontabchange ... childContent>` + `<Tab id label icon content>` usage keeps working exactly as before. `<Tab>` now renders no DOM of its own; it registers its props with the parent via context, and `<Tabs>` renders the real tab buttons + panels from the registered entries
  - **Responsive modes work reliably** — `scroll` clips and scrolls within the container (hidden scrollbar), `wrap` flows tabs onto multiple rows (real flex-wrap), `menu` collapses overflowing tabs into a `⋯` button at the end of the strip that opens a floating menu of hidden tabs. Selecting a hidden tab swaps its position with the last-visible tab so the selection stays in the strip. Uses the same `fluent-menu`/`fluent-menu-item` styling as QuickGrid's context menu for visual consistency. The old `clip` mode was removed — `scroll` + `menu` cover every real-world need it did
  - **Menu-mode ellipsis truncation** — when the next tab doesn't fully fit but there's ≥ 60px of remaining strip space, it's kept in the strip as the last visible tab and capped via `max-width`; the label truncates with `…` (icon + close button stay intact) rather than being kicked into the overflow menu. Edge case where the very first tab alone is wider than the strip also truncates rather than clipping raw
  - **Menu `⋯` button pinned to the end of the strip** — via flex `margin-left: auto` (horizontal) / `margin-top: auto` (vertical) so its position doesn't shift with the width of the last-visible tab. Shadow tablist copy stays in flow so its natural width is measurable (`:not(.fluent-tab-shadow)` scopes the margin to the real button)
  - **Measurement is feedback-loop-free** — `menu` mode uses an off-screen "shadow" tablist that renders every tab at natural width. `visibleCount` is computed by cumulative-summing shadow widths against the real tablist's `clientWidth`. Without the shadow, showing/hiding the overflow button would swing the measurement in a cycle
  - **Scroll arrow buttons** — in `responsive="scroll"` mode, `‹` and `›` buttons appear at the ends automatically when there's overflow, and scroll by 80% of the tablist width on click. Hidden when the tablist fits. Absolute-positioned over the strip edges so toggling them doesn't change the tablist's `clientWidth` (which would itself feedback-loop)
  - **Animated full-width active indicator** — a 2px bar that slides between tabs with a cubic-bezier `transform`/`width` transition (vs FluentUI's 20px static sub-tab micro-indicator). `translate(x, y)` on both axes so the indicator correctly tracks the active tab's row in `responsive="wrap"` multi-row layouts

  - **Vertical orientation** fully supported — strip on the left with a vertical border, indicator on the left edge. Long labels auto-ellipsis so one wide tab doesn't inflate the whole strip
  - **`stripWidth` / `stripHeight` props** — cap the strip's cross-axis. Most useful in `orientation="vertical"` where the default is natural-width (widest label wins); `stripWidth="200px"` gives a predictable sidebar and each tab's label auto-ellipsises when needed
  - **Swipe navigation** — horizontal-swipe on the tabpanels container (vertical-swipe in vertical orientation) navigates prev/next tab. Dominant-axis guard (`|Δmain| ≥ 50px` AND `|Δmain| ≥ |Δcross| × 1.5`) so scrolling panel content doesn't hijack the gesture; touches starting on interactive elements (`input`, `button`, `textarea`, `select`, links, contenteditable, ARIA `slider`/`spinbutton`) are ignored so form controls keep their gestures.   - **Native `title` tooltip** — each tab button gets `title={tab.label}` so hover reveals the full text, especially useful for ellipsis-truncated labels

  - Deprecated `overflow={...}` prop — the dropdown-overflow feature was rarely used, not auto-populated from real overflow, and is superseded by `responsive="menu"`. Warns to the console if set

But that class is used in two modes: a portalled floating overlay (dropdowns, toolbars) *and* a plain static wrapper that `NavLink` / `NavExpander` render around every sidebar item.
